## What the decisions say

No systemic deviations. Every loop-back finding was routed to the artifact
that owned it and resolved in the next cycle. No override was exercised
except O-1 (the p1-001 deferral), and that override records that the flow
proceeds with an unresolved finding under a signed human decision, not that
the finding is dismissed.

The deferrals consolidated under `docs/findings/data-prep-price-path.md`:

- **p1-001 F-3** — pin real reference checksums from an accepted reference
  build. Blocked by the parse failure.
- **p1-002 T-5/T-12** — dbt singular test execution for the provenance and
  dangling-endpoint checks. Blocked by the parse failure.
- **p1-003 T-15** — dbt singular test execution for the coverage-report
  metrics. Blocked by the parse failure.
- **p1-003 real-mart demonstration** — running the report against real marts.
  Blocked by the parse failure.

The finding is a defect in the data-preparation package: `stg_retail_listing.sql`
references `retail_aisle_listing` and `retail_search_listing`, which no model,
seed, or source produces. The seeds are present; the block is not a setup
gap. Three downstream models (`int_product_identity.sql`,
`int_price_fulfillment_candidates.sql`, `edge_fulfills.sql`) consume the
stale staging model; a parallel staging model (`stg_price_mapped_nutrients`)
reads the seed that does exist and is not consumed by anything. The fix is
the package owner's; the finding names two candidate resolutions.

## Retro

### Went well

- **The reviews caught every real problem.** p1-001's review found eleven
  findings (three blockers); p1-002's found the association was unwired and
  unverified; p1-003's took three rounds and each found a real gap. None of
  these were caught by CI alone — CI runs the tests, and the tests were
  weaker than the specs required. The review stage is where the difference
  was found.
- **The deferral mechanism worked.** Four deferrals, all pointing at one
  upstream defect, all recorded honestly. No feature fabricated evidence to
  hide the block; no test was weakened to pass.
- **The kit's structure held.** The state machine, the hash checks, the
  ownership rules, and the gate commands all did their jobs. When the
  tasks_hash drifted in p1-002 (an unauthorized edit to a frozen task), the
  gate caught it. When p1-003's spec drifted, the hash caught it. The
  mechanism paid for itself.

### Went badly

- **Five loops across four features; every one was verification or plumbing,
  none was a design failure.** The features were designed correctly; the
  tests didn't prove them, or the wiring between artifacts wasn't tested
  end to end. That's a systematic gap, not an instance of bad luck.
- **The interfaces between artifacts weren't tested end to end.** p1-002's
  fixtures didn't exercise the real pipeline (mocked `compute_mart_entries`);
  p1-003's association went through manifest → Makefile → model with no test
  covering the whole path; p1-003's test fixtures reimplemented dbt's Jinja
  rendering with regexes and fell behind when the model's Jinja changed.
  Each loop closed one layer of the same gap.
- **The price-path defect survived the entire phase.** Every feature was
  proven with fixtures; none ran the real pipeline. The defect was invisible
  until phase-end verification, when the pipeline was actually attempted.
  A single end-to-end test at phase start would have surfaced it on day one.

- p1-002-provenance-graph-model: 1 implementation loop

## Proposed changes

1. **Plan-prompt addition — integration test per interface.** Add a rule to
   `prompts/plan.md` and `skills/planning/SKILL.md`: *"Every interface the
   plan names must have one task whose `Done when` is a test that exercises
   the full path from producer to consumer, not each side in isolation."*
   This would have caught p1-002's mocked pipeline, p1-003's unwired
   association, and p1-003's regex-based dbt fixture at the plan stage
   rather than the review stage. **Route: constitution amendment** (if a
   rule with a Check is preferred) **or plan-prompt change** (if the kit's
   prompts are considered the right home).

2. **Name the crawler → data-preparation interface as a contract.** The
   defect's root cause is that two packages exchange data without a declared
   contract: the crawler produces `raw_matched_food_prices.csv` and
   `raw_unmatched_food_prices.csv`; the data-preparation staging model reads
   `retail_aisle_listing` and `retail_search_listing`. Neither package
   documents the boundary, and the naming/schema mismatch is what broke the
   build. **Route: proposal or constitution** — a rule requiring that
   cross-package data boundaries be declared (a `sources.yml` on the
   consumer side, a documented output contract on the producer side).

3. **Phase p2 prerequisite — resolve `docs/findings/data-prep-price-path.md`
   before p2 begins, or accept fixture-based verification for p2.** The
   finding is a defect in a package this effort does not own. Two coherent
   positions:
    - **Block p2.** The reasoning phase needs real marts; without a working
      pipeline, p2's reasoning is verified against fixtures only. Delay p2
      until the finding is resolved.
    - **Proceed with fixtures.** p2's features are unit-level
      (constraint filtering, cost arithmetic, solver feasibility) and can be
      verified with constructed inputs. Proceed, and record that the
      end-to-end demonstration is deferred to the finding's resolution.

   **Recommendation: proceed with fixtures, and record the finding as a
   p2 risk.** p2's reasoning logic doesn't depend on the shape of the
   real marts; it depends on the contract the marts provide, which fixtures
   can simulate. The end-to-end demonstration becomes a p2 exit criterion
   if the finding is resolved before p2 closes, or a follow-up if not.
   **Route: roadmap re-plan.**

4. **Roadmap — add a follow-up item for the finding.** The finding is
   tracked in `docs/findings/data-prep-price-path.md`. Add a roadmap
   reference so it doesn't fall off: either a note in the phase p2
   prerequisites, or a roadmap-level "Cross-phase findings" section that
   lists external defects affecting multiple phases. **Route: roadmap
   re-plan.**

5. **Retro learning — the phase's own process.** The five loops, all on
   verification, indicate the kit's checks are working but the plans weren't
   structured to prove their interfaces. Proposed: for phase p2, every
   feature's plan includes at least one integration test that exercises
   the real path; the plan review rejects plans whose test strategy is
   entirely fixture- or mock-based. **Route: constitution amendment** if
   the rule applies project-wide, **plan-prompt change** if per-phase.
   (Same substance as #1; listed separately because it applies to the
   phase's process rather than to the kit's prompts.)
